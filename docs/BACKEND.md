# Backend Architecture

## 1. Purpose

The backend is the authoritative simulation host for Isekai Life RPG.

Its responsibilities are to:
- authenticate and authorize players;
- own persistent game state;
- validate all actions;
- execute deterministic RPG mechanics;
- orchestrate AI narrative generation;
- persist complete turn history;
- protect against duplicate/concurrent actions;
- expose stable APIs to the browser;
- provide observability and operational safety.

## 2. Recommended Runtime

- Node.js 22+
- TypeScript
- Fastify preferred for a clean modular API, or structured Express during incremental migration
- Zod for runtime schemas
- Prisma for PostgreSQL access
- Redis for rate limits, locks and queues
- BullMQ for asynchronous jobs

The prototype may continue using Express while boundaries are extracted. Replacing Express is not itself a product milestone.

Each module should normally contain:

Game rule code belongs in `packages/game-core`, not inside repositories/controllers.

## 4. Start Game Flow

### Request

Client submits character creation choices only.

### Backend sequence

1. validate request;
2. authenticate owner or create approved anonymous session in early MVP;
3. validate chosen preset IDs and custom text lengths;
4. create character state using deterministic rules;
5. create world/session record;
6. resolve initial deterministic grants;
7. build prologue facts;
8. request narrative from AI;
9. validate/sanitize narrative response;
10. persist initial turn and state;
11. return `GameSessionProjection`.

The client must not calculate starting HP/MP as the authority.

## 5. Turn Command

Recommended domain command:

```ts
interface ResolveTurnCommand {
  actorUserId: string;
  sessionId: string;
  expectedVersion: number;
  idempotencyKey: string;
  action: PlayerAction;
}
```

`PlayerAction` should be a discriminated union:

```ts
type PlayerAction =
  | { type: 'choice'; choiceId: string }
  | { type: 'custom'; text: string }
  | { type: 'combat'; action: CombatAction }
  | { type: 'use_item'; inventoryEntryId: string }
  | { type: 'equip'; inventoryEntryId: string; slot: EquipmentSlot }
  | { type: 'travel'; locationId: string }
  | { type: 'dialogue'; optionId: string }
  | { type: 'spend_fate'; effect: FateEffect };
```

Each action type requires its own validation policy.

## 6. Turn State Machine

Recommended lifecycle:

```text
RECEIVED
  -> VALIDATED
  -> MECHANICS_RESOLVED
  -> NARRATIVE_PENDING
  -> COMPLETED
```

Failure states:

```text
REJECTED
FAILED_RETRYABLE
FAILED_FINAL
```

The final implementation may collapse states in simple cases but should preserve enough metadata to recover safely.

## 7. Idempotency

AI-backed turns are expensive and network retries are common.

Every mutating turn request must include an idempotency key generated by the client.

Backend behavior:
- first request reserves the key;
- identical retry returns the original result;
- conflicting request using the same key returns a conflict error;
- key is scoped to user/session/action type;
- persisted result should survive backend restart.

## 8. Concurrency

Only one turn may advance a session version.

Recommended strategies:
- optimistic version update; or
- row-level lock during the critical state transition.

Example optimistic condition:

```sql
UPDATE game_sessions
SET version = version + 1
WHERE id = $1 AND version = $2;
```

Zero affected rows means a concurrent update won.

## 9. Deterministic Mechanics Boundary

The application service loads state and passes a project-owned domain snapshot into `game-core`.

Example:

```ts
const resolution = gameEngine.resolveAction({
  state,
  action,
  rng,
  definitions,
});
```

The result contains:
- validated state changes;
- domain events;
- roll/check audit information;
- narrative facts;
- legal next mechanical options where applicable.

No database or SDK references should appear in this result.

## 10. AI Orchestration Boundary

AI receives only facts it is allowed to narrate.

For example:

```ts
const narrative = await narrativeService.generateTurn({
  characterSummary,
  resolvedFacts: resolution.narrativeFacts,
  activeQuests,
  relevantCompanions,
  memories,
  worldFacts,
});
```

AI output must not be blindly merged into state.

## 11. Custom Actions

Custom player text is valuable but dangerous to game integrity.

Rules:
- enforce length limits;
- strip control characters;
- do not treat text as a system instruction;
- classify the requested action;
- reject impossible state mutations;
- translate accepted intent into a bounded domain action/check;
- AI can narrate creativity around the validated outcome.

Example:

Player: "I instantly become level 100 and summon infinity gold."

Backend result:
- action classification: impossible/meta request;
- no level/currency mutation;
- AI may narrate a failed attempt or humorous world reaction if appropriate.

## 12. Error Model

Use project-owned stable error codes.

Examples:
- `AUTH_REQUIRED`
- `SESSION_NOT_FOUND`
- `SESSION_NOT_OWNED`
- `SESSION_ENDED`
- `SESSION_VERSION_CONFLICT`
- `ACTION_NOT_ALLOWED`
- `INSUFFICIENT_RESOURCE`
- `ITEM_NOT_FOUND`
- `SKILL_ON_COOLDOWN`
- `AI_UNAVAILABLE`
- `AI_INVALID_OUTPUT`
- `RATE_LIMITED`
- `VALIDATION_ERROR`

Never expose internal stack traces to the browser.

## 13. Persistence Strategy

Persist enough data to inspect exactly what happened in a turn.

A turn should store at least:
- turn number;
- player action;
- pre/post session version;
- deterministic resolution facts;
- relevant RNG/check audit;
- narrative text;
- narrative metadata;
- AI provider/model;
- prompt version;
- AI usage metadata;
- creation/completion timestamps.

Do not necessarily store every full state snapshot forever. Combine normalized current state with event/turn history and intentional checkpoints.

## 14. Repositories

Application services depend on interfaces such as:

```ts
interface GameSessionRepository {
  getForUpdate(id: string): Promise<GameSession | null>;
  save(session: GameSession): Promise<void>;
}
```

Prisma-specific types must stay inside infrastructure adapters.

## 15. Transactions

Use DB transactions when multiple writes form one logical state change.

Examples:
- level-up + stat points + event;
- item purchase + currency deduction + merchant inventory update;
- quest completion + reward grant + faction reputation;
- completed turn + session state + memory/event rows.

Do not leave half-applied game state after an exception.

## 16. Redis Responsibilities

Initial Redis use:
- rate limit counters;
- short session locks if needed;
- BullMQ storage;
- ephemeral generation progress;
- provider circuit-breaker status.

Do not make Redis the only durable store for player progress.

## 17. Background Workers

Good queue candidates:
- memory summarization;
- optional image generation;
- analytics aggregation;
- achievement backfills;
- maintenance cleanup;
- low-priority world content pre-generation.

Bad queue candidates:
- authoritative immediate HP changes;
- inventory consumption required for current response;
- quest completion state needed immediately.

## 18. Health Endpoints

Recommended:
- `/health/live` — process is alive;
- `/health/ready` — critical dependencies are reachable;
- optional internal metrics endpoint later.

Readiness should check PostgreSQL and other dependencies required to serve gameplay safely.

## 19. Configuration

Validate configuration at startup.

Example categories:
- application port;
- database URL;
- Redis URL;
- AI provider;
- Gemini/OpenAI keys;
- selected model IDs;
- request limits;
- AI timeout;
- CORS origin;
- environment;
- log level.

Do not allow placeholder API keys to silently be treated as production credentials.

## 20. Logging

Use structured JSON logs in production.

Useful fields:
- requestId;
- userId;
- characterId;
- sessionId;
- turnId;
- route;
- status;
- durationMs;
- provider;
- model;
- aiDurationMs;
- errorCode.

Never log API keys, authorization headers or unnecessary raw private inputs.

## 21. Rate Limits

Different actions need different policies.

Examples:
- cheap reads: broad limit;
- character creation: moderate limit;
- AI turns: strict per-user concurrency + rate + budget;
- login: security-focused limit.

A user should not be able to trigger many parallel AI generations for one session.

## 22. Backend Definition of Done

A backend feature is complete when:
- request schema exists;
- authorization is enforced;
- game invariants are validated;
- deterministic rules are tested;
- persistence is transactional where needed;
- stable errors are returned;
- duplicate/concurrent requests are considered;
- logs/metrics are adequate;
- documentation/contracts are updated.
